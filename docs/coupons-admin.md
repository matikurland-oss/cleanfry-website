# מערכת קופונים ומעקב מכירות — הגדרה, הפעלה ומעבר

## מה נבנה

- **מסד נתונים (Supabase Postgres)** הוא מקור האמת לקופונים, להזמנות ולתשלומים. הסכמה נמצאת ב-`supabase/migrations/`.
- **`/admin`** הוא אזור ניהול בעברית: יצירה, עריכה, השהיה והפעלה של קופונים, דוח ביצועים והזמנות שדורשות תשומת לב.
- **תמחור בצד השרת**: `api/create-order.ts` מחשב את הסכום המחייב בעצמו (`shared/pricing.ts`) ויוצר הזמנה ממתינה לפני פתיחת התשלום.
- **אימות תשלומים**: `api/tranzila-notify.ts` שומר כל הודעה, מאמת את העסקה מול ה-API של טרנזילה ורק אז רושם רכישה, באופן אטומי וללא כפילויות.
- **ניסיונות חוזרים**: `api/cron/reconcile.ts` מעבד שוב אירועים שנכשלו ושולח שוב מיילי אישור שלא נשלחו.

### יחידות ומוסכמות
| נושא | מוסכמה |
|---|---|
| סכומים | אגורות, מספר שלם (`total_agorot = 22900` = ₪229) |
| אחוז הנחה | אחוז רגיל: `18.00` = 18% (ב-Edge Config הישן: שבר, `0.18`) |
| אחוז הנחה מקסימלי | 25% (כולל). נאכף ב-API, במסד הנתונים ובייבוא |
| עיגול הנחה | לשקל שלם, חצי ומעלה כלפי מעלה (כמו הקוד הקודם) |
| משלוח | ₪35. חינם כשסכום המוצרים **אחרי הנחה** ≥ ₪199. איסוף עצמי תמיד חינם |
| זמנים | נשמרים ב-UTC. בממשק ובדוחות לפי `Asia/Jerusalem` |
| תוקף מחיר | 15 דקות מיצירת ההזמנה |

## הגדרה

### 1. פרויקט Supabase
פרויקט בדיקה כבר קיים: `cleanfry-test` (eu-central-1), ושתי המיגרציות הוחלו עליו.

לייצור צרו פרויקט נפרד (למשל `cleanfry`, באזור eu-central-1). החילו עליו את שני הקבצים ב-`supabase/migrations/` לפי הסדר, ב-SQL Editor או ב-`supabase db push`.

### 2. משתני סביבה
ראו `.env.example`. ב-Vercel הגדירו אותם ב-Project Settings → Environment Variables, בנפרד ל-Preview ול-Production:

| משתנה | מאיפה |
|---|---|
| `SUPABASE_URL`, `VITE_SUPABASE_URL` | Supabase → Project Settings → API → Project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → API → service_role (**סודי**, צד שרת בלבד) |
| `VITE_SUPABASE_ANON_KEY` | Supabase → API → anon / publishable (ציבורי) |
| `ORDER_SIGNING_SECRET` | כבר קיים ב-Vercel. אפשר להשאיר אותו |
| `CRON_SECRET` | מחרוזת אקראית חדשה (`openssl rand -base64 32`) |
| `TRANZILA_APP_KEY`, `TRANZILA_SECRET` | ראו "מפתחות API של טרנזילה" למטה |

### 3. יצירת מנהל ראשון
1. ב-Supabase → Authentication → Users → **Add user** יוצרים משתמש עם אימייל וסיסמה חזקה, ומסמנים Auto Confirm.
2. ב-SQL Editor מריצים:
   ```sql
   insert into admin_users (user_id, email)
   select id, email from auth.users where email = 'owner@example.com';
   ```
3. ב-Authentication → Providers → Email מומלץ **לכבות "Allow new users to sign up"**. כך רק משתמשים שנוצרו ידנית יוכלו להתחבר. גם אם ההרשמה פתוחה, רק מי שמופיע ב-`admin_users` מקבל גישה ל-API הניהול.

להסרת מנהל: `delete from admin_users where email = '...';`

### 4. הרצה מקומית
```bash
npm install
npm test                      # בדיקות יחידה ו-API (vitest)
npm run dev:api               # שרת API מקומי על 5210, טוען .env.local
npm run dev                   # האתר על 3000, /api מופנה לשרת המקומי
```
בדיקות מסד הנתונים: מריצים את `supabase/tests/db_checks.sql` ב-SQL Editor של פרויקט **הבדיקה**. הכול מתבטל בסוף, וכל השורות צריכות להחזיר `ok = true`.

## מפתחות API של טרנזילה — חובה לספירת רכישות
הודעת ה-notify של טרנזילה **אינה חתומה**. לכן השרת מאמת כל עסקה בפנייה משלו ל-API של טרנזילה, לפי מספר העסקה (`index`).

**בלי מפתחות:**
- תשלומים נשמרים כ"ממתינים לאימות".
- הם לא נספרים בדוחות ולא נשלח עליהם מייל אישור.
- הם מופיעים ב-/admin תחת "דורש תשומת לב", ובינתיים יש לבדוק אותם ידנית בממשק הניהול של טרנזילה.

**עם מפתחות:** ה-cron מאמת אוטומטית גם את מה שהצטבר קודם.

להשגת המפתחות:
1. בקשו מטרנזילה (ממשק הניהול או התמיכה) **Application key + Secret** ל-API, עבור הטרמינל `cleanfry`.
2. בקשו מהם לאשר את **כתובת החיפוש של עסקאות (search transactions)** ואת **שמות השדות בתשובה**. ברירת המחדל בקוד: `https://api.tranzila.com/v1/transactions`, עם השדות `index`, `processor_response_code`, `amount`, `currency_code`, `remarks`. **חובה שהתשובה תכלול את `remarks` של העסקה**: כך השרת מוודא שהעסקה שייכת להזמנה הזו ולא לקוח אחר באותו סכום (מספרי עסקאות רצים וניתנים לניחוש). בלי השדה הזה שום תשלום לא יאומת. אם הכתובת שונה, הגדירו `TRANZILA_TRANSACTIONS_SEARCH_URL`. אם שמות השדות שונים, עדכנו את `parseTransactionSearch` ב-`api/_lib/tranzila.ts`.
3. בדקו בסביבת Preview עם עסקה אמיתית קטנה, ובטלו אותה מיד אחר כך. וודאו שהיא מופיעה כמאומתת בדוח.

הקוד נכשל "סגור": אם התשובה לא במבנה הצפוי, ההזמנה נשארת "ממתינה לאימות" ולא מסומנת כשולמה.

## מעבר מ-Edge Config
1. **בדיקה מקדימה** (לא כותבת דבר):
   ```bash
   npm run import-coupons -- --dry-run
   ```
   הכלי מציג אילו קופונים ייווצרו, אילו כבר קיימים ואילו לא תקינים ומדוע.
2. **ייבוא**: `npm run import-coupons`. מותר להריץ שוב: קוד שכבר קיים מדולג.
3. השוו ב-/admin שכל הקודים, האחוזים ותאריכי התפוגה נכונים.
4. **פריסה**: מרגע הפריסה `validate-coupon` ו-`create-order` קוראים **רק** ממסד הנתונים. אין עוד קוד שקורא קופונים מ-Edge Config.
5. השאירו את Edge Config כמו שהוא (קפוא) עד שהמערכת יציבה, כגיבוי לחזרה אחורה. אל תערכו אותו יותר: כל ניהול נעשה מ-/admin.

> הערה: `src/shoppingIlPromo.ts` מכיל תאריך סיום קבוע לתצוגת לוגו Shopping IL. הוא לא קורא מ-Edge Config ואינו קשור לתקפות הקופון, שנקבעת עכשיו רק במסד הנתונים.

### חזרה אחורה במקרה תקלה
1. ב-Vercel → Deployments בוחרים את הפריסה האחרונה לפני המעבר → **Instant Rollback**. היא קוראת מ-Edge Config, שנשאר ללא שינוי.
2. הזמנות ששולמו בזמן שהמערכת החדשה פעלה נשמרות במסד הנתונים ונשלח עליהן מייל. הן לא אובדות.
3. מתקנים, ופורסים מחדש את הגרסה החדשה.

### נתוני עבר
הדוחות מתחילים לצבור נתונים אמינים מרגע ההפעלה. לא מיובאות רכישות היסטוריות: המקור היחיד הקיים הוא מיילים מ-Formspree, והם לא מאומתים מול הסליקה. אם תרצו בעתיד לייבא היסטוריה מדוח עסקאות של טרנזילה, זה ייעשה ככלי נפרד ויסומן בנפרד בדוח.

## פריסה
1. החילו את המיגרציות על פרויקט Supabase של הסביבה.
2. הגדירו את משתני הסביבה ב-Vercel.
3. פרסו ל-Preview ובדקו: התחברות ל-/admin, יצירת קופון, ותהליך תשלום עד טופס טרנזילה (בלי לחייב).
4. הריצו את הייבוא, ואז פרסו ל-Production.

**Cron:** `vercel.json` מריץ את `/api/cron/reconcile` פעם ביום (03:00 UTC), כי זה המקסימום בתוכנית Hobby של Vercel. בתוכנית Pro מומלץ לשנות ל-`*/10 * * * *`. ה-cron הוא רשת ביטחון; ה-notify עצמו מעבד את רוב העסקאות בזמן אמת.

## אבטחה
- כל הטבלאות עם RLS בלי policies: מפתח ה-anon (שנמצא בדפדפן) לא יכול לקרוא או לכתוב דבר. הגישה רק דרך פונקציות השרת עם `service_role`.
- כל קריאה ל-`/api/admin/*` בודקת JWT של Supabase וחברות ב-`admin_users`. ההרשאה נשלחת בכותרת `Authorization` ולא ב-cookie, ולכן אין חשיפה ל-CSRF.
- תשובות API ו-`/admin` עם `Cache-Control: no-store`; `/admin` עם `X-Robots-Tag: noindex`.
- הגבלת קצב לפי IP (מגובב): בדיקת קופון עד 20 בדקה, יצירת הזמנה עד 15 ב-10 דקות.
- `validate-coupon` מחזיר רק את תוצאת הקוד שנבדק, עם הודעה זהה לקוד מושהה ולקוד שלא קיים.
- `coupon_audit` מתעד מי יצר, ערך, השהה או הפעיל ומתי, ללא סודות. מ-notify נשמרים רק שדות בטוחים (בלי פרטי כרטיס ות"ז).

## מגבלות ידועות
1. **אימות תשלומים תלוי במפתחות API של טרנזילה** (ראו למעלה). עד שיוגדרו, אין ספירה אוטומטית של רכישות.
2. **תוקף 15 דקות לא נאכף אצל טרנזילה.** ה-iframe לא תומך בתפוגה. האתר מסתיר את טופס התשלום אחרי 15 דקות ומחייב יצירת הזמנה חדשה. אם בכל זאת הגיע תשלום מאוחר, הוא **נרשם** (הכסף התקבל בפועל) ומסומן "שולם אחרי פקיעת המחיר" לבדיקה. Handshake V2 של טרנזילה (`thtk`, תוקף של כ-20 דקות) יכול לנעול את הסכום בצד טרנזילה. הוא דורש את אותם מפתחות API ולא מומש בגרסה זו.
3. **הסכום נשלח ל-iframe כשדה טופס.** לקוח יכול לשנות אותו בדפדפן. במקרה כזה האימות מול טרנזילה יחזיר סכום שונה, וההזמנה תסומן "אי-התאמת סכום" ולא תיספר. Handshake (סעיף 2) ימנע זאת מראש.
4. **החזרים**: אין עדיין מקור מאומת, ולכן הדוח מציג "לא זמין". הטבלה `refunds` מוכנה לשימוש עתידי.
5. מדיניות הניסיונות החוזרים של טרנזילה ל-notify לא מתועדת. לכן כל אירוע נשמר לפני העיבוד, ו-cron מעבד שוב מה שנכשל.
6. התשלום הכפול (שתי עסקאות מאושרות לאותה הזמנה) נרשם במלואו בסך שנגבה ומסומן לבדיקה. ההחזר ללקוח נעשה ידנית בטרנזילה.
